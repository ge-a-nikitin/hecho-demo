# Отчёты в Qase TestOps

[← Документация](./README.md) · [English version](../en/qase.md)

Страница описывает, как автоматические тесты связаны с проектом `HECHO` в Qase TestOps: где живёт каталог кейсов, как он синхронизируется с проектом, кто и когда отправляет результаты и как это проверить локально. Источники истины — каталог `apps/api/src/test-support/qase/` и workflow `.github/workflows/qase.yml`; при изменении процесса обновляйте эту страницу.

Главное правило: Qase нужен только для отчётов. Ни unit-, ни интеграционный набор не требуют сети, поэтому проверки в pull-request остаются офлайн, а результаты отправляются после мержа в `main`.

## Каталог кейсов

- Кейсы описаны в `apps/api/src/test-support/qase/cases/` — по модулю на продуктовую область, а `qase-manifest.ts` реэкспортирует их как единый каталог: ключ, путь suite (повторяет дерево `describe`), заголовок, severity, priority, layer и то содержание, которое видит человек в TestOps, — описание на английском о том, зачем нужен кейс, предусловия, classic-шаги (`action` и ожидаемый результат), необязательные постусловия, а также Qase type и behavior.
- Тесты вызывают `qc("<key>", "<title>")` из `apps/api/src/test-support/qase-case.ts`; хелпер падает на этапе сбора тестов, если ключа нет или заголовок разошёлся с каталогом, и остаётся пустышкой, пока ID не созданы, поэтому офлайн-прогоны и проверки в pull-request не зависят от Qase.
- Кейс опознаётся по тегу `order-desk:<key>`, поэтому переименование или перенос записи каталога обновляет существующий кейс и сохраняет его ID и историю прогонов. Когда запись уходит из каталога, кейс не удаляется: в API TestOps нет архива кейсов, поэтому синхронизация переносит его в `Archive / <исходный верхний suite>`, сохраняя теги и результаты, а вернувшаяся запись возвращает тот же кейс на место.
- Каталог проверяется офлайн: `apps/api/src/test-support/qase-manifest.spec.ts` контролирует уникальность ключей, пути suite и слой, отсутствие устаревших ID, наличие ID у каждого ключа каталога, непустое содержание, предусловия и не меньше трёх шагов у api-кейсов и ровно один spec на ключ в обе стороны. `apps/api/src/test-support/qase/sync-plan.spec.ts` так же покрывает правила синхронизации — идентичность по тегу, архивацию, восстановление и дубли тегов — не обращаясь к сети.

## Синхронизация с проектом

- `pnpm qase:sync --dry-run` только печатает план и ничего не меняет в проекте, но завершается с кодом 1, если план не пуст: это проверка дрейфа между каталогом и проектом, и её выполняет CI после мержа.
- `pnpm qase:sync` создаёт недостающие suite и кейсы в Qase TestOps, перезаписывает кейсы, у которых разошлось содержание или метаданные, и обновляет `apps/api/src/test-support/qase-case-ids.ts` числовыми ID. Синхронизация идемпотентна: повторный запуск сообщает, что все кейсы не изменились.
- Каждое описание заканчивается строкой `_Automated by <spec>_`, собранной из вызовов `qc()`, поэтому перенос файла теста обновляет его кейс на следующей синхронизации.
- `qase-case-ids.ts` — сгенерированный файл: его пишет только синхронизация, вручную его не правят.

## Локальные прогоны с отчётом

- `pnpm --filter @order-desk/api test:qase` отправляет unit-набор, `pnpm --filter @order-desk/api test:qase:integration` — интеграционный. Обе команды выставляют `QASE_MODE=testops`, создают прогон, привязывают каждый результат к его кейсу, завершают прогон и печатают ссылку на него.
- `pnpm qase:run` делает то же для повседневной работы: синхронизирует каталог и прогоняет unit-набор с отчётом.
- Параметризованный тест отправляет несколько результатов на один кейс (`does not allow cancelling an invoiced order` выполняется для двух статусов), поэтому unit-прогон из 84 тестов даёт 84 результата на 83 кейса.
- Ссылка на прогон имеет вид `https://app.qase.io/run/HECHO/dashboard/<id>`; при разборе лога её достаёт `grep -oE 'Test run link: https://[^ ]+' | tail -1 | awk '{print $NF}'`, потому что перед ней в выводе бывают другие адреса.

## Прогоны в CI

- Прогоны отчитываются только после мержа. Workflow `.github/workflows/qase.yml` запускается на пуш в `main` и вручную: job `catalogue` проверяет каталог через `qase:sync --dry-run` и падает, если каталог и проект разошлись, jobs `unit` и `integration` прогоняют наборы с `QASE_MODE=testops` и пишут ссылку на прогон в summary, а job `publish` добавляет обе ссылки комментарием в смерженный pull-request.
- Pull-request токена Qase не получает, поэтому его проверки остаются офлайн, а fork не может отправить результаты в проект. Токен лежит в секрете репозитория `QASE_TESTOPS_API_TOKEN` и доступен только этому workflow.
- Дефекты в Qase не связываются с GitHub Issues: найденные дефекты чинятся в том же pull-request вместе с регрессионным тестом.

## Конфигурация

- Файл `apps/api/qase.config.json`: проект `HECHO`, US-кластер `qase.io`, `mode: off`, поэтому обычные прогоны остаются офлайн.
- API-токен берётся из `QASE_TESTOPS_API_TOKEN` в игнорируемом git файле `.env`.
- `QASE_MODE`, `QASE_TESTOPS_PROJECT`, `QASE_TESTOPS_API_HOST` и `QASE_TESTOPS_RUN_TITLE` переопределяют конфиг, когда нужны другие настройки.

## Если прогон не появился

1. Убедитесь, что `QASE_MODE=testops`: при `off` набор проходит без отправки результатов.
2. Проверьте `QASE_TESTOPS_API_TOKEN`: без него `qase:sync` и отчётные прогоны завершаются ошибкой авторизации.
3. Посмотрите job `catalogue`: его падение означает, что каталог и проект разошлись, поэтому сначала выполните `pnpm qase:sync` и закоммитьте `qase-case-ids.ts`.
4. Проверьте теги кейса в TestOps: результат находит кейс по `order-desk:<key>`, поэтому переименованный ключ без синхронизации оставит результат без кейса.

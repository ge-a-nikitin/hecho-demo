## Назначение

Приложение одной организации для приёма заказов от зарегистрированных заказчиков, распределения и выполнения работ, учёта времени и выставления внутренних счетов.

Этот документ фиксирует согласованные требования, статус реализации и инструкции запуска. Основа монорепозитория, схема PostgreSQL и основные доменные сценарии backend API реализованы. Во frontend доступны публичный лендинг, авторизация и панели заказчика, исполнителя и администратора с профилем и карточками заказов. API и frontend запускаются в Docker Compose вместе с PostgreSQL и SeaweedFS. Автоматизированные сквозные проверки ведутся в отдельном учебном репозитории и не входят в этот проект; здесь поддерживаются стабильные QA-локаторы и devtools API.

## Согласованный функционал

### Публичная главная страница

- До входа пользователь видит публичный лендинг, который объясняет назначение доски заказов и основной процесс работы с заказами.
- На лендинге доступны переход ко входу и регистрация заказчика.
- Лендинг общедоступен и не показывает данные заказов или внутреннюю информацию организации.

### Роли и доступ

- **Заказчик** создаёт заказы и отслеживает свои заказы.
- **Исполнитель** принимает и выполняет заказы.
- **Администратор** управляет пользователями и всеми заказами.
- Заказчик может самостоятельно зарегистрироваться на сайте.
- Регистрация заказчика открыта любому посетителю; аккаунт активируется сразу после регистрации.
- Учётные записи исполнителей создаёт администратор.
- Начальная учётная запись администратора создаётся отдельной CLI-командой из `ADMIN_EMAIL` и `ADMIN_PASSWORD`; повторный запуск не меняет уже существующего администратора.
- При создании исполнителя администратор задаёт начальный пароль и передаёт его вне приложения. Почасовую ставку администратор не задаёт: исполнитель устанавливает и изменяет её самостоятельно в профиле. Сброс пароля заказчика или исполнителя выполняет администратор; самостоятельное восстановление заказчиком отложено до подключения email.
- Выход из аккаунта доступен в боковой панели на широких экранах и в верхней панели на мобильных.
- Учётные записи деактивируются, а не удаляются, чтобы сохранить историю заказов и счетов.
- Перед деактивацией исполнителя администратор должен переназначить все его незавершённые заказы.
- Один пользователь имеет одну роль. Вход заказчика, исполнителя и администратора осуществляется через разные маршруты/панели; данные авторизации одной роли не дают доступ к панелям других ролей.
- Заказчик видит только созданные им заказы и связанные с ними комментарии и счета.

### Создание и распределение заказов

- Заказчик может выбрать исполнителя при создании заказа либо оставить заказ неназначенным.
- Неназначенные заказы доступны администратору для распределения и исполнителям в общем пуле.
- В общем пуле все исполнители видят полное описание заказа и вложения.
- Заказ закрепляется за первым исполнителем, который взял его из пула.
- Администратор также может распределять заказы.
- Заказ выполняет один исполнитель. Администратор может переназначить заказ; история сохраняет прежнего исполнителя.
- Выбранный или назначенный исполнитель может отказаться от заказа; заказ возвращается в пул неназначенных.
- В черновике заказчик может менять все данные. После отправки основные параметры заказа не редактируются; заказчик может добавлять комментарии.
- Название, описание и категория обязательны. Срок выполнения, вложения/файлы и место выполнения или адрес необязательны.
- Категории работ создаёт администратор. Заказчик выбирает категорию при создании заказа; исполнитель видит категорию и может фильтровать по ней список заказов. Исполнитель не назначает категории.
- Списки заказов во всех панелях поддерживают поиск по названию и описанию, фильтрацию по статусу и категории и постраничный вывод по 10 заказов.
- Заказчик, назначенный исполнитель и администратор могут оставлять комментарии в истории заказа; комментарии видны всем участникам.

### Статусы

Согласованный маршрут заказа:

- **Новая** — черновик заказчика.
- После отправки черновик становится **Ждёт распределения**, если исполнитель не выбран, или **Назначена**, если выбран.
- Администратор может назначить исполнителя заказу, ожидающему распределения. Исполнитель, который первым берёт заказ из пула, закрепляет его за собой; заказ становится **Назначена**.
- Назначенный исполнитель предлагает количество часов и рассчитанную сумму. Заказчик подтверждает предложение; до подтверждения начинать работу нельзя.
- После подтверждения заказ переходит в **В работе**.
- Исполнитель отправляет завершённую работу на проверку: **На проверке**.
- Если заказчик просит исправления, заказ переходит в **Нужны исправления**. Когда исполнитель приступает к исправлениям, заказ возвращается в **В работе**; после исправлений исполнитель повторно отправляет заказ на проверку: **На проверке**.
- После приёмки работы заказчиком администратор выставляет счёт: **Выставлен счёт**.
- После приёмки работы заказчик сообщает об оплате, и заказ ожидает проверки платежа администратором в статусе **Выставлен счёт**. После проверки администратор подтверждает оплату, и заказ переходит в **Счёт оплачен**. Завершение — отдельное действие администратора после подтверждения поступления денег; только тогда заказ становится **Завершена**.
- Заказ может быть **Отменён** согласно правилам ниже.

### Отмена заказа

- До начала работ заказ может отменить заказчик или администратор.
- До начала работ причина отмены не обязательна.
- После начала работ отменить заказ может только администратор; причина обязательна.
- После выставления счёта заказ отменить нельзя: неоплаченный счёт аннулируется, после чего можно выставить новый. Оплаченный счёт неизменяем и не аннулируется; корректировка после оплаты не входит в текущий процесс.

### Ставка, оценка и учёт времени

- Исполнитель задаёт и изменяет почасовую ставку в своём профиле; администратор не может её установить или изменить. Ставки могут различаться.
- Назначенный исполнитель предлагает количество часов. Сумма рассчитывается автоматически: ставка исполнителя × предложенные часы.
- Заказчик подтверждает предложенное количество часов и рассчитанную сумму до начала работ.
- Если заказчик отклоняет предложение, он оставляет комментарий, заказ возвращается в пул неназначенных, а в истории заказа фиксируется возврат из этапа согласования.
- Ставка фиксируется для заказа на момент предложения и не меняется при последующем изменении ставки в профиле.
- Фактически затраченное время исполнитель вводит вручную одной суммарной записью с комментарием.
- Исполнитель может редактировать суммарное время, пока заказ находится в статусе «В работе». Фактическое время и комментарий видны исполнителю, заказчику и администратору.
- Фактическое время учитывается отдельно и не меняет сумму счёта, рассчитанную по согласованным часам.

### Счёт и оплата

- После приёмки работы заказчиком администратор выставляет счёт.
- Счёт формируется в приложении и доступен для скачивания в PDF.
- Заказчик оплачивает счёт банковским переводом вне приложения.
- После перевода заказчик отмечает в приложении, что оплатил счёт, и обязан прикрепить подтверждение оплаты (чек/квитанцию). Без файла подтверждения отправить уведомление об оплате нельзя.
- Подтверждение оплаты хранится отдельно от обычных вложений заказа и доступно заказчику и администраторам; исполнителю платёжный документ не показывается.
- Отметка заказчика переводит оплату в состояние «Ожидает проверки», но сама по себе не подтверждает поступление денег и не завершает заказ.
- Администратор проверяет поступление денег и приложенный документ, затем вручную подтверждает оплату. После подтверждения счёт становится оплаченным, а заказ переходит в статус **Счёт оплачен**; это ещё не завершает заказ.
- Завершение заказа — отдельное действие администратора в статусе **Счёт оплачен**. Оно фиксирует `completedAt` и переводит заказ в **Завершена**; без оплаченного счёта завершение недоступно.
- Если подтверждение некорректно или платёж не найден, администратор не подтверждает оплату; заказ остаётся открытым до исправления ситуации.
- При отклонении чека администратор обязан указать причину. Заказчик видит причину и может загрузить новый чек; предыдущие чеки и решения остаются в истории.
- Чек загружается в отдельное поле/раздел оплаты, с теми же ограничениями загрузки файлов (любой тип, максимум 1 MB), и не считается обычным вложением работы.
- Автоматическая обработка платежей через внешнего провайдера не входит в MVP и может быть добавлена позднее.
- На первом этапе счёт является внутренним, не юридическим документом.
- Валюта счёта — USD.
- PDF-счёт содержит номер, дату, имена заказчика и исполнителя, согласованные часы, ставку и итоговую сумму.
- Суммы округляются до 2 знаков после точки. Номер счёта уникален и последователен в пределах года, формат: `INV-ГГГГ-000001`.
- Счёт хранит снимки имён заказчика и исполнителя, часов, ставки и суммы на момент выставления; изменение профиля или заказа не меняет уже выставленный счёт. Последовательность номеров ведётся отдельным счётчиком на каждый год и увеличивается атомарно в транзакции.
- Неоплаченный счёт можно аннулировать с указанием причины и администратора, который выполнил действие, а затем выставить новый. Аннулированный счёт и его номер сохраняются; номер не используется повторно. У заказа может быть только один действующий счёт. Оплаченный счёт неизменяем; корректировка после оплаты не входит в текущий процесс.

### Файлы и уведомления

- К заказу можно прикреплять файлы любых типов размером не более 1 MB на файл.
- Уведомления не входят в MVP.

## Технические ограничения и пожелания

- Актуальная ER-диаграмма и ограничения модели данных описаны в [database-schema.md](./database-schema.md).
- Один TypeScript-монорепозиторий с `pnpm workspaces`.
- Backend: NestJS, REST API, Swagger/OpenAPI.
- Frontend: одно приложение React + Vite + TypeScript с панелями `/customer`, `/executor` и `/admin`.
- В каждой панели для списков заказов, профиля и других самостоятельных разделов используются отдельные страницы.
- Карточка заказа открывается поверх списка: на широких экранах — центрированный диалог с приглушённым фоном, на мобильных — нижняя шторка, которую можно смахнуть вниз. Детали заказа имеют собственный URL: прямой переход, обновление страницы и навигация браузера должны работать, не теряя контекст списка там, где он доступен.
- Интерактивные элементы интерфейса должны иметь стабильные QA-локаторы (предпочтительно атрибуты `data-testid`) для внешних тестовых сценариев. Локаторы не должны зависеть от CSS-классов, структуры DOM или отображаемого текста. Автоматизированные e2e-тесты ведутся в отдельном учебном репозитории и не запускаются из этого проекта.
- База данных: PostgreSQL; доступ к данным и миграции: Prisma.
- Авторизация: Better Auth с хранением данных в PostgreSQL. Для всех панелей используется одна система сессий; отдельные маршруты и серверная проверка роли запрещают доступ к чужим панелям и API.
- Devtools API включается только явным `DEVTOOLS_ENABLED=true` и защищается отдельным `x-devtools-api-key` из `DEVTOOLS_API_KEY`. Ручки позволяют создать пользователя заданной роли (CUSTOMER/EXECUTOR/ADMIN) по email и паролю, получить список пользователей выбранной роли, изменить email/пароль и активность пользователя по ID, а также загрузить/удалить фиксированный набор тестовых данных. Пароль и API key не возвращаются; переданный пароль хешируется Better Auth и существующие сессии пользователя отзываются после изменения email/пароля или деактивации. Seed-пароль хранится только локально в `DEVTOOLS_SEED_PASSWORD`; JSON-фикстура хранит только данные набора, не секреты. Ключ задаётся администратором окружения, сейчас через `.env`; при необходимости размещения devtools в production их следует включать только после явного решения, хранить ключ и seed-пароль в защищённом secrets vault и ограничивать сетевой доступ. Для полного сброса проекта предусмотрены ручка `POST /api/devtools/reset` (обязательное подтверждение `{"confirm":"reset-all-data"}`) и команда `pnpm db:reset`: они удаляют все данные, пользователей, сессии и объекты файлов, затем заново создают единственного администратора из `ADMIN_EMAIL`/`ADMIN_PASSWORD`.
- Массовые демонстрационные данные детерминированы и описаны декларативной JSON-фикстурой в `apps/api/src/devtools/fixtures/test-data.json`. Повторный запуск заменяет фиксированный набор; очистка удаляет зарезервированные seed-записи вместе со счетами, чеками и другими зависимыми записями, созданными для seed-заказов, и не затрагивает данные, не связанные с seed-набором. Если на seed-пользователя или seed-категорию ссылаются вручную созданные записи, очистка возвращает конфликт с требованием сначала убрать эти связи.
- API проверяет DTO на сервере (лишние поля запрещены), сессию, активность пользователя, роль, права на конкретный заказ и допустимость переходов состояния; клиентская валидация не считается границей безопасности. Ошибки REST API возвращаются с машинным полем `code` (`BAD_REQUEST`, `UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT`, `PAYLOAD_TOO_LARGE`, `INTERNAL_SERVER_ERROR` и др.). Необработанные серверные детали не отправляются клиенту, ошибки валидации не содержат значения полей. Интерфейс переводит код ошибки в понятное сообщение и показывает ошибки/результаты действий в закрываемом toast-уведомлении сверху страницы.
- Интерфейс локализован на английский (по умолчанию), русский и испанский языки. Переключатель языка доступен на лендинге, страницах входа и регистрации, в панелях и на странице 404, а выбор сохраняется в `localStorage` под ключом `order-desk.language`. Параметр `?lang=en|ru|es` задаёт язык при открытии и имеет приоритет над сохранённым выбором; неизвестное значение игнорируется. Язык интерфейса не меняет URL и не переводит пользовательские данные (названия заказов и категорий, имена, комментарии). Тексты интерфейса находятся в `apps/web/src/i18n/messages/{en,ru,es}.ts`, а даты, числа, денежные суммы и единицы времени форматируются по выбранной локали.
- Локальное файловое хранилище: SeaweedFS через S3-совместимый API.
- Сервисы запускаются в Docker Compose. Локальные порты по умолчанию: `6200` frontend, `6201` API, `6202` PostgreSQL, `6203` SeaweedFS S3 API, `6204` SeaweedFS Admin UI; значения переопределяются в `.env`.

## Интерфейс и дизайн-система

Стили веб-приложения разделены по слоям в `apps/web/src/styles/` и подключаются в `main.tsx` в порядке каскада: `tokens.css` (дизайн-токены и база), `system.css` (кнопки, состояния, переключатель языка), `landing.css`, `panel.css`, `orders.css`, `overlays.css` (шторка и toast), `motion.css` (фолбэки доступности).

- Токены описывают типографическую шкалу в `rem` (минимальный размер интерфейсного текста — 12 px), шкалу отступов, три радиуса, три уровня теней, материалы (`--material-*`), motion-параметры (`--response-*`, `--ease-*`) и цвета текста с контрастом не ниже 4.5:1 для мелкого текста. Размеры в `rem` нужны, чтобы интерфейс следовал пользовательской настройке размера текста.
- Отклик: каждый интерактивный элемент отвечает на нажатие (`:active`) в момент pointer-down, а не по завершении клика; `touch-action: manipulation` убирает задержку тапа. Hover-эффект не заменяет отклик на нажатие.
- Материалы: шапка лендинга, топбар и сайдбар панели, мобильная панель вкладок, toast и шторка заказа — полупрозрачные слои с `backdrop-filter`; жёсткие разделители заменены затухающими линиями, мобильная панель вкладок учитывает `env(safe-area-inset-bottom)`.
- Моушен: собственный spring-интегратор `apps/web/src/motion/spring.ts` с параметрами `response` и `damping` (аналог Apple damping/response), без внешних зависимостей. Шторка деталей заказа описана в `apps/web/src/motion/sheet.ts`: жест на Pointer Events с захватом указателя, отслеживание 1:1 с учётом точки захвата, сопротивление за верхней границей, передача скорости отпускания в spring и решение «закрыть или вернуть» по знаку скорости. Анимация всегда стартует от текущего значения на экране, поэтому начатый жест прерывает и перенаправляет её без рывка.
- Жест закрытия работает из верхней зоны шторки (ручка и заголовок). Контент заказа сохраняет нативную прокрутку, поэтому жест не конфликтует со скроллом; на широких экранах перетаскивание отключено.
- Модальное поведение: при открытой детали заказа блокируется прокрутка страницы, фокус переходит внутрь, `Tab`/`Shift+Tab` не выходят за пределы шторки, `Esc` и нажатие на затемнение закрывают её, после закрытия фокус возвращается на элемент, с которого её открыли.
- Доступность: поддержаны `prefers-reduced-motion` (движение заменяется коротким крест-фейдом, наклон и подъём карточек отключаются), `prefers-reduced-transparency` (материалы становятся непрозрачными) и `prefers-contrast: more` (плотные границы, контрастный текст, усиленный фокус-ринг).

## План реализации

Предпочтительный порядок — снизу вверх, от базы данных к интерфейсам:

1. **Основа репозитория и базы данных (готово):** созданы workspace и Docker Compose; добавлены Prisma-модели и PostgreSQL-миграции для пользователей, категорий, заказов, истории статусов и назначений, оценок, учёта времени, комментариев, вложений и счетов. Схема учитывает деактивацию пользователей, снимки данных в счетах, атомарную годовую последовательность номеров, аннулирование неоплаченного счёта и выпуск нового без удаления истории.
2. **Backend/API (основные сценарии реализованы):** готовы NestJS API, Better Auth, серверная проверка ролей и деактивированных аккаунтов, Swagger/OpenAPI, health endpoint, начальный администратор, категории, административное управление исполнителями и заказчиками, назначение/переназначение/отказ/отмена заказа, предложения оценок и ответы заказчика, выполнение и проверка работы, учёт времени и комментарии. Также реализованы вложения в SeaweedFS с ограничением 1 MB, PDF-счета с поддержкой кириллицы, последовательная годовая нумерация, аннулирование и перевыставление неоплаченного счёта, отправка заказчиком чека оплаты с ручной проверкой/отклонением администратором, перевод заказа в `INVOICE_PAID` после подтверждения оплаты и отдельное административное завершение заказа. Отклонение оценки заказчиком требует комментария. Добавлены devtools API с флагом включения и проверкой API key: создание/список/обновление пользователей, повторяемый JSON seed с очисткой seed-записей и связанных с ними счетов и чеков, а также полный сброс проекта с очисткой файлов и пересозданием администратора из `.env`. Проверены сборка, типы и миграции; для сценариев заказа добавлен интеграционный набор, который работает против отдельного эфемерного стека.
3. **Frontend (основные сценарии реализованы):** настроены React, Vite и TypeScript; добавлены публичный лендинг, регистрация/вход через Better Auth, передача сессионных cookies, проверка роли для панелей заказчика, исполнителя и администратора, навигация и профиль. В профиле пользователь может изменить имя и email после подтверждения текущим паролем, а также сменить пароль с отзывом остальных сессий; изменение email применяется сразу, без подтверждения нового адреса, и сбрасывает признак `emailVerified`. Карточка заказа открывается по собственному URL поверх списка: на широких экранах как центрированный диалог, на мобильных как нижняя шторка со свайпом вниз; в ней показаны участники, статусы и история, оценки, учтённое время, файлы, счета, чеки и комментарии с учётом прав API. Заказчик загружает категории и заказы, создаёт заказ с необязательным выбором исполнителя, сохраняет черновик, редактирует и отправляет его, принимает/отклоняет оценку исполнителя (при отклонении указывает причину), принимает работу или запрашивает исправления, прикрепляет файлы к черновику, оставляет комментарии, отменяет заказ до начала работ, а также отправляет чек к выставленному счёту и видит результаты проверки. Исполнитель загружает доступные и назначенные заказы, берёт заказ из пула, предлагает оценку, учитывает время, отказывается от задания и отправляет работу на проверку или продолжает исправления. Администратор просматривает заказы, назначает/переназначает их, выставляет счета, скачивает PDF счёта, аннулирует неоплаченный счёт с указанием причины и выставляет новый, проверяет/отклоняет чеки, подтверждает оплату и отдельно завершает оплаченный заказ. На отдельной странице пользователей администратор видит исполнителей и заказчиков, включая неактивных, создаёт исполнителей без ставки, редактирует имя исполнителя, сбрасывает пароли, активирует и деактивирует аккаунты. Ошибки API показываются в интерфейсе; интерактивные элементы размечены стабильными `data-testid`. Списки заказов поддерживают поиск, фильтры по статусу и категории и постраничный вывод; на мобильных выход из аккаунта доступен в верхней панели. Проверены production-сборка и целевые проверки; сквозные сценарии поддерживаются в отдельном репозитории.
4. **Docker Compose (готово):** добавлены сборки API и frontend, frontend раздаётся Nginx с поддержкой прямых переходов по URL. Compose запускает все сервисы, ждёт готовности PostgreSQL, применяет Prisma-миграции перед стартом API и проверяет его health endpoint. Порты сервисов настраиваются через `.env`.
5. **Сквозные проверки (вне репозитория):** автоматизированные e2e-проверки выполняются в отдельном учебном репозитории. В этом проекте остаются unit- и интеграционные тесты API, devtools API и стабильные `data-testid` для внешних сценариев; Playwright и e2e-набор в проект не входят.

Интеграция Better Auth с NestJS и Prisma проверена регистрацией, входом и получением сессии; регистрация создаёт пользователя с ролью `CUSTOMER`.

## Открытые вопросы

- Уточнить формат имени отображения администратора, создаваемого из `ADMIN_EMAIL`/`ADMIN_PASSWORD`.
- Описать схемы ответов в Swagger: сейчас документируются параметры, тела запросов и допустимые значения перечислений, а тела ответов возвращаются без типизированных схем. Для полного контракта понадобятся response DTO или отдельные сериализаторы ответов.
- Настроить CSP и rate limiting для `/api/auth/*` средствами Cloudflare (Transform Rules и WAF Rate limiting). Строгая CSP требует отдельной настройки Swagger UI, поэтому решение отложено до публикации. Закрытие Swagger через Cloudflare Access тоже пока не настроено.

## Запуск проекта локально

### Требования

- Docker Engine с Docker Compose v2 (`docker compose`); Docker Desktop подходит для Windows и macOS.
- Git для клонирования репозитория.
- Свободные локальные порты, перечисленные ниже.
- Node.js `22.18` или новее и pnpm `12.15` требуются только для разработки и запуска команд workspace на хосте. Для обычного Compose-запуска Node.js/pnpm на хосте устанавливать не нужно.

### Первый запуск через Docker Compose

1. Клонируйте репозиторий и перейдите в его корень.
2. Создайте локальный файл окружения: `cp .env.example .env` (в Windows PowerShell: `Copy-Item .env.example .env`).
3. Откройте `.env` и замените все значения `replace-this-*` уникальными локальными паролями/секретами. Задайте `ADMIN_EMAIL` и `ADMIN_PASSWORD` для первого администратора. Пароли PostgreSQL должны быть URL-safe (буквы, цифры и `._~-`), поскольку API использует их в `DATABASE_URL`.
4. Соберите образы и запустите все сервисы: `docker compose up --build -d`. Первый запуск может занять несколько минут. API дождётся PostgreSQL и автоматически применит все миграции перед тем, как стать доступным.
5. Создайте начальную учётную запись администратора: `docker compose exec api pnpm --filter @order-desk/api db:seed:admin`. Эта команда безопасна для повторного запуска и не меняет уже созданного администратора.
6. Откройте frontend, войдите под `ADMIN_EMAIL`/`ADMIN_PASSWORD`; из панели администратора можно создавать исполнителей. Заказчики могут зарегистрироваться самостоятельно.

### Адреса и порты по умолчанию

| Сервис | Адрес с хоста | Назначение |
|---|---|---|
| Frontend | `http://localhost:6200` | Приложение |
| API | `http://localhost:6201/api` | REST API и Better Auth |
| Swagger | `http://localhost:6201/api/docs` | Контракт и интерактивная документация API: схемы и примеры тел запросов, допустимые значения перечислений |
| Проверка API | `http://localhost:6201/api/health` | Health endpoint |
| PostgreSQL | `localhost:6202` | База данных |
| SeaweedFS S3 API | `http://localhost:6203` | Хранение файлов |
| SeaweedFS Admin UI | `http://localhost:6204` | Администрирование локального хранилища |

Порты привязаны к `127.0.0.1`, поэтому сервисы доступны только с локальной машины. Внутри Compose-сети API использует PostgreSQL по адресу `postgres:5432` и SeaweedFS по адресу `seaweedfs:8333`.

### Настройка портов и адресов

Если порт занят, измените соответствующее значение в `.env` и пересоберите/перезапустите Compose:

- `WEB_PORT` — порт frontend на хосте.
- `API_PORT` — порт API на хосте.
- `POSTGRES_PORT` — порт PostgreSQL на хосте (обновите порт в `DATABASE_URL`, если запускаете миграции с хоста).
- `S3_PORT` — порт S3 API на хосте.
- `SEAWEEDFS_ADMIN_PORT` — порт SeaweedFS Admin UI на хосте.

При изменении портов frontend/API обновите связанные origin/URL в `.env`: `VITE_API_URL` должен указывать на публичный адрес API с `/api`, `BETTER_AUTH_URL` — на тот же адрес с `/api/auth`, `FRONTEND_ORIGIN` — на origin frontend. Затем выполните `docker compose up --build -d`, чтобы пересобрать frontend с новым `VITE_API_URL`. Для параметров БД/S3 Docker-сервисы используют внутренние имена сети; `DATABASE_URL` и `S3_ENDPOINT` в контейнере API автоматически переопределяются Compose.

### Повседневные команды

- Статус сервисов: `docker compose ps`.
- Логи всех сервисов: `docker compose logs -f`; одного сервиса, например API: `docker compose logs -f api`.
- Перезапуск после изменения конфигурации/кода: `docker compose up --build -d`.
- Запуск после перезагрузки ПК: контейнеры объявлены с `restart: "no"`, поэтому не стартуют автоматически вместе с системой — поднимите стек вручную командой `docker compose up -d`. Docker также не перезапускает контейнеры после падения; если нужен автоматический перезапуск при сбоях и автозапуск при загрузке, верните `restart: unless-stopped` в `docker-compose.yml`.
- Остановка без удаления данных: `docker compose down`.
- Сброс всех данных без остановки контейнеров: `pnpm db:reset` или, при включённых devtools, `POST /api/devtools/reset` с заголовком `x-devtools-api-key`. Заказы, счета, файлы, пользователи и сессии удаляются, администратор из `.env` создаётся заново.
- Полная очистка локальной базы и файлов: `docker compose down -v` **удалит данные PostgreSQL и SeaweedFS без возможности восстановления**.

### Разработка с запуском приложений на хосте

Для работы с hot reload установите Node.js и pnpm, затем выполните `pnpm install`. Создайте `.env` по инструкциям выше и запустите только инфраструктуру: `docker compose up -d postgres seaweedfs`. Проверьте Prisma схему/клиент (`pnpm db:validate`, `pnpm db:generate`), примените миграции через `pnpm db:migrate`, затем создайте администратора командой `pnpm db:seed:admin`. В отдельных терминалах запустите API `pnpm --filter @order-desk/api dev` и frontend `pnpm --filter @order-desk/web dev`. Для браузера frontend обычно доступен на `http://localhost:6200`, API — на `http://localhost:6201`; `VITE_API_URL` и `FRONTEND_ORIGIN` должны соответствовать фактическим адресам.

### Автоматические тесты

- Unit-тесты API на Vitest лежат рядом с кодом (`apps/api/src/**/*.spec.ts`) и работают офлайн, без базы и сети: `pnpm --filter @order-desk/api test`. Конфигурация — `apps/api/vitest.config.ts`, тесты сгруппированы по функциям (`Orders` → `Lifecycle`, `Invoices` → `Payment reports` и так далее), поэтому дерево отчёта повторяет структуру кода.
- Интеграционные тесты вызывают настоящий HTTP API: `pnpm --filter @order-desk/api test:integration`. Глобальный setup сам собирает и поднимает отдельный стек `docker-compose.test.yml` (проект `order-desk-test`, порты `7101` и `7102`), ждёт `/api/health`, в начале прогона очищает базу через `POST /api/devtools/reset`, а в конце удаляет контейнеры вместе с данными (`docker compose down -v`). Отдельный проект и отдельные порты гарантируют, что набор не затронет данные разработки или production, а сброс данных упадёт с понятной ошибкой, если стек не тестовый.
- Сейчас интеграционный набор один — жизненный цикл заказа: черновик → пул → конкурентный захват → оценка → выполнение → проверка → приёмка, отказ от оценки, исправления, отмена, а также права доступа и валидация запросов. Нужен Docker; первый запуск собирает образ API и поэтому занимает несколько минут.
- Переменные для нестандартного окружения: `TEST_API_URL` (адрес API, по умолчанию `http://127.0.0.1:7101`), `TEST_STACK_MANAGED=false` (использовать уже запущенный стек), `TEST_STACK_KEEP=true` (оставить контейнеры после прогона для разбора), `TEST_COMPOSE_FILE` (другой compose-файл).
- Проверка типов покрывает и тестовый код: `pnpm typecheck` запускает `tsc --noEmit` для `src` и `tsc --noEmit -p apps/api/tsconfig.test.json` для `test` и конфигов Vitest.

### Devtools и тестовые данные

Для локальной необходимости использовать devtools API установите `DEVTOOLS_ENABLED=true`, задайте случайный `DEVTOOLS_API_KEY` длиной не менее 32 байт и `DEVTOOLS_SEED_PASSWORD` в `.env`; запросы отправляют ключ в заголовке `x-devtools-api-key`. Пока флаг не равен `true`, вся группа devtools отвечает `404`, как будто ручек нет, и скрыта из Swagger; после включения они появляются в `/api/docs` вместе с описанными телами запросов, а без корректного ключа возвращают `401`. В Swagger UI ключ вводится в поле `x-devtools-api-key` каждой ручки. Значение роли чувствительно к регистру: допустимы только `CUSTOMER`, `EXECUTOR`, `ADMIN`, и в Swagger у параметра `role` и у поля `role` в теле запроса есть выпадающий список этих значений. Ручки доступны через Swagger/Postman: `POST /api/devtools/users`, `GET /api/devtools/users?role=CUSTOMER|EXECUTOR|ADMIN`, `PATCH /api/devtools/users/{id}`, `POST /api/devtools/seed` (заменить фиксированный набор) и `DELETE /api/devtools/seed` (удалить его). Seed создаёт аккаунты `devtools.admin@example.test`, `devtools.customer@example.test`, `devtools.executor@example.test` с паролем из `DEVTOOLS_SEED_PASSWORD`. Очистка удаляет seed-пользователей, категории, заказы, а также счета и подтверждения оплаты, относящиеся к seed-заказам. Если seed-запись используется вручную созданными данными, например seed-исполнитель назначен на обычный заказ, очистка возвращает конфликт: сначала переназначьте или удалите такие записи. Объекты файлов в SeaweedFS при очистке seed-набора не удаляются; их удаляет только полный сброс. Не включайте devtools без необходимости и не используйте production-ключи в локальной среде.

Полный сброс проекта выполняет `POST /api/devtools/reset` с телом `{"confirm":"reset-all-data"}`. Запрос удаляет всех пользователей вместе с аккаунтами и сессиями, категории, заказы с комментариями, оценками, назначениями, историей статусов, учётом времени и вложениями, счета с подтверждениями оплаты и нумерацию счетов, после чего в той же транзакции создаёт единственного администратора из `ADMIN_EMAIL`/`ADMIN_PASSWORD`. Обязательное поле `confirm` защищает от случайного вызова: без него или с другим значением API возвращает `400`, а при неверном ключе — `401`; если `ADMIN_EMAIL` или `ADMIN_PASSWORD` не заданы, сброс отклоняется до удаления данных. Все сессии отзываются, поэтому войти нужно заново паролем из `.env`, а нумерация счетов начинается с 1. После коммита бакет SeaweedFS очищается полностью, включая осиротевшие объекты (`"purgeFiles": false` оставляет файлы); если хранилище недоступно, база остаётся сброшенной, а в ответе будет `files.error` — объекты нужно удалить вручную. Ту же операцию без запущенного API выполняет команда `pnpm db:reset`: она берёт `DATABASE_URL`, `S3_*` и `ADMIN_*` из `.env` и завершается с ненулевым кодом, если файлы удалить не удалось. Ответ содержит созданного администратора, количество удалённых записей по типам и результат очистки файлов.

## Развёртывание на домашней ВМ (Cloudflare Tunnel)

Продовый запуск использует тот же `docker-compose.yml` и overlay `docker-compose.prod.yml`. Отдельного прокси-контейнера нет: TLS завершается на границе Cloudflare, туннель `cloudflared` работает службой systemd на той же ВМ и ходит в `127.0.0.1:8080`, а единственная точка входа приложения — nginx из образа `web`: он отдаёт статику SPA и проксирует `/api/*` в контейнер `api:6201`. Входящие порты на роутере открывать не нужно — туннель сам устанавливает исходящее соединение.

```text
браузер → Cloudflare (TLS, кеш, WAF) → cloudflared на ВМ → nginx:8080 → api:6201 или статика SPA
```

### Что нужно

- ВМ (подойдёт QEMU-виртуалка на домашнем компьютере) с Docker Engine и Docker Compose v2, git и curl; 2+ ГБ RAM и место под volumes `postgres_data` и `seaweedfs_data`.
- Домен, зона которого делегирована на Cloudflare и находится в статусе Active: приложение публикуется на `hecho-demo.hius2.fyi`, поэтому зона `hius2.fyi` должна быть Active.
- Токен туннеля из Cloudflare Zero Trust.

### Схема окружения и секретов

Конфигурация разделена на две части, чтобы секреты не попадали в git:

| Где | Что лежит | Зачем |
|---|---|---|
| `deploy/prod.env` (в git) | `DOMAIN`, `WEB_PORT`, `TRUST_PROXY`, `DEVTOOLS_ENABLED`, `COMPOSE_FILE`, `POSTGRES_USER`, `POSTGRES_DB`, `ADMIN_EMAIL`, `S3_ACCESS_KEY`, `S3_BUCKET`, `SEAWEEDFS_ADMIN_USER` | Не секреты: изменения видны в диффах и проходят ревью |
| GitHub → Environments → `production` → secret `PROD_ENV_SECRETS` (многострочный) | `POSTGRES_PASSWORD`, `BETTER_AUTH_SECRET`, `ADMIN_PASSWORD`, `S3_SECRET_KEY`, `SEAWEEDFS_ADMIN_PASSWORD` | Шифруется, доступно только workflow этого environment, маскируется в логах как `***` |
| `/etc/cloudflared/` на ВМ | токен туннеля | Не относится к приложению и не хранится в репозитории |
| `.env` на ВМ (создаётся деплоем, права `600`) | склейка `deploy/prod.env` и `PROD_ENV_SECRETS` | Единственный формат, который читает `docker compose` |

`deploy/prod.env` содержит `COMPOSE_FILE=docker-compose.yml:docker-compose.prod.yml`, поэтому на ВМ достаточно коротких команд `docker compose ...`. Для локальной проверки overlay подключается явно: `docker compose -f docker-compose.yml -f docker-compose.prod.yml config`.

Честная граница: при таком способе секреты существуют в открытом виде в `.env` на диске ВМ и в переменных процессов контейнеров. Их защищают права `600` и отдельный пользователь ВМ; сам runner имеет доступ к Docker socket, то есть фактически к root на ВМ, поэтому доступ к ВМ и её диску нужно ограничивать отдельно (например, шифрованием диска).

### Однократная подготовка ВМ

1. Установите Docker Engine с Compose v2, git и curl; клонируйте репозиторий в каталог, от которого будет работать runner.
2. Подключите туннель (токен выдаёт Cloudflare при создании туннеля):

   ```bash
   sudo cloudflared service install <TUNNEL_TOKEN>
   sudo systemctl enable --now cloudflared
   systemctl status cloudflared
   ```

3. В Cloudflare Zero Trust создайте Public Hostname `hecho-demo.hius2.fyi` с пустым путём и сервисом `HTTP://localhost:8080`. DNS-запись создаёт сам туннель, поэтому конфликтующие A/CNAME удалите заранее. В настройках зоны включите Always Use HTTPS (HSTS — по желанию).
4. Зарегистрируйте self-hosted runner (Settings → Actions → Runners) и установите его службой:

   ```bash
   mkdir -p ~/actions-runner && cd ~/actions-runner
   curl -fsSLO <ссылка на actions-runner-linux-x64.tar.gz со страницы runner'а>
   tar xzf actions-runner-linux-x64.tar.gz
   ./config.sh --url https://github.com/<owner>/<repo> --token <runner-token> --labels order-desk --unattended
   sudo ./svc.sh install "$USER" && sudo ./svc.sh start
   ```

   Репозиторий публичный, поэтому workflow намеренно запускается только на `push` в `main` и вручную через `workflow_dispatch`. Событие `pull_request` добавлять нельзя: код из форка выполнялся бы на ВМ.

### Деплой

Workflow `.github/workflows/deploy.yml` при каждом push в `main` (или ручном запуске):

1. делает checkout;
2. собирает `.env` из `deploy/prod.env` и секрета `PROD_ENV_SECRETS` с правами `600` и проверяет, что файл остаётся неотслеживаемым;
3. выполняет `docker compose up -d --build --remove-orphans`;
4. ждёт `http://127.0.0.1:8080/` и `http://127.0.0.1:8080/api/health` (до 200 с), при неудаче печатает `docker compose ps` и логи `api`/`web`;
5. удаляет висячие образы.

Обновление вручную на ВМ: `git pull && docker compose up -d --build`.

### Первый запуск

1. Заполните `deploy/prod.env` (`ADMIN_EMAIL` — реальный адрес администратора) и добавьте секрет `PROD_ENV_SECRETS` в environment `production`; секреты удобно генерировать через `openssl rand -base64 32`, пароль PostgreSQL должен быть URL-safe.
2. Запустите workflow и дождитесь зелёного статуса.
3. Один раз создайте администратора вручную:

   ```bash
   docker compose exec api pnpm --filter @order-desk/api db:seed:admin
   ```

   Деплой администратора не создаёт: `ADMIN_EMAIL`/`ADMIN_PASSWORD` используются только командами seed и полного сброса.
4. Проверьте прод: `curl -I https://hecho-demo.hius2.fyi`, `curl https://hecho-demo.hius2.fyi/api/health`, откройте `https://hecho-demo.hius2.fyi/api/docs` и войдите в интерфейс под администратором. Загрузите файл в заказ — это проверяет и cookie-сессию, и SeaweedFS.

### Ротация секретов

Общий порядок: измените значение в GitHub → запустите деплой заново. Workflow перезапишет `.env` и пересоздаст контейнеры. Особые случаи:

| Секрет | Что учесть |
|---|---|
| `BETTER_AUTH_SECRET` | Все сессии инвалидируются — пользователям нужно войти заново. |
| `ADMIN_PASSWORD` | Влияет только на `db:seed:admin` и полный сброс; пароль существующего администратора не меняется. |
| `POSTGRES_PASSWORD` | Пароль уже инициализированной базы сам не изменится: выполните `docker compose exec -T postgres psql -U <POSTGRES_USER> -d <POSTGRES_DB> -c "ALTER USER <POSTGRES_USER> WITH PASSWORD '<новый пароль>'"`, после чего обновите секрет и задеплойте. |
| `S3_SECRET_KEY`, `SEAWEEDFS_ADMIN_PASSWORD` | Данные в volumes сохраняются; после деплоя проверьте загрузку файла и вход в админку SeaweedFS. |

### Эксплуатация

- Статус: `docker compose ps`; логи приложения — `docker compose logs -f`, только API — `docker compose logs -f api`, туннель — `journalctl -u cloudflared -f`.
- Перезагрузка ВМ: контейнеры с `restart: unless-stopped`, а также службы `cloudflared` и runner'а поднимаются автоматически. В локальном режиме без overlay контейнеры по-прежнему не перезапускаются.
- Бэкап базы: `docker compose exec -T postgres pg_dump -U <POSTGRES_USER> <POSTGRES_DB> | gzip > backup-$(date +%F).sql.gz`. Файлы лежат в volume `seaweedfs_data`; его копируют, остановив `seaweedfs`, или через `docker run --rm -v <project>_seaweedfs_data:/data -v "$PWD":/backup alpine tar czf /backup/files.tgz /data`.
- Смена домена: измените `DOMAIN` в `deploy/prod.env`, добавьте новый Public Hostname в туннель и задеплойте. `FRONTEND_ORIGIN` и `BETTER_AUTH_URL` вычисляются из `DOMAIN`, а frontend собирается с относительным `VITE_API_URL=/api`, поэтому пересобирать код под домен не нужно. Пользователям придётся войти заново: старые cookie привязаны к прежнему домену.
- `TRUST_PROXY=true` (не число): перед API три перехода — Cloudflare, cloudflared и nginx, а origin недоступен напрямую. Без этого протокол определяется как `http` (cookie без `Secure`) и IP клиента оказывается неверным.
- После `docker compose restart api` nginx может отвечать `502`: контейнер получил новый адрес. Помогает `docker compose restart web`; штатный `up -d --build` пересоздаёт сеть целиком и этой проблемы не даёт.
- Devtools в проде выключены (`DEVTOOLS_ENABLED=false`): группа ручек отвечает `404` и скрыта из Swagger, включая полный сброс данных.
- Публикуется только `127.0.0.1:8080` для туннеля; порты `api`, `postgres` и `seaweedfs` остаются на `127.0.0.1` для отладки.

### Ограничения продовой конфигурации

- Swagger опубликован открыто — это решение проекта. Если нужен закрытый доступ, накройте путь `/api/docs*` приложением Cloudflare Access: маршруты туннеля менять не нужно.
- Нет CSP и rate limiting на `/api/auth/*`: это настраивается средствами Cloudflare (Transform Rules и WAF Rate limiting), а не в репозитории. Учитывайте, что Swagger UI несовместим со строгой CSP.
- `docker compose down -v` удаляет данные PostgreSQL и SeaweedFS; для бэкапа используйте `pg_dump` и копирование volumes, а не удаление стека.
- Отдельного CI-workflow пока нет: проверки типов, сборка, unit- и интеграционные тесты API запускаются локально (`pnpm typecheck`, `pnpm build`, `pnpm --filter @order-desk/api test`, `pnpm --filter @order-desk/api test:integration`) и будут добавлены в Actions вместе с расширением тестов.
